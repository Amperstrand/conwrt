# NR7101 9eSIM provisioning — handover, 2026-11-26

Status: **router access and transport are solved; the profile install itself
fails at the ES10b load stage, and the free test code is now spent.** Target:
silent.link (free test profile first, then the $1 "nadanada"), on a 9eSIM in a
Zyxel NR7101 now running OpenWrt 25.12.4.

Unit-level identifiers are deliberately omitted (see conwrt AGENTS.md
"Specimen Inventory and Network Details Belong in a Private Project").

**Superseded claim:** an earlier revision of this doc said provisioning was
"blocked on the router having no WAN". That is no longer the blocker. The
router still has no WAN, but `lpac`'s APDU and HTTP legs are separable, so
APDU now stays local on the router (fast) and only HTTP is relayed to the
provisioning host. See §1 "Transport, solved" and issue **#862**.

## 1. What worked

**Flashing / install**
- One authorized `sysupgrade -n -f` from the 24.10.5 initramfs to 25.12.4.
  Refused to force, refused to retry, refused to power-cycle. `sysupgrade -T`
  returned 0; both image and config SHA-256s matched before the write.
- Result verified by reading the router, not a log: OpenWrt **25.12.4**,
  kernel **6.12.87**, squashfs `/rom` + UBIFS `/overlay` (persistent, not
  initramfs), board name and MAC matching the physical label.

**Recovering management afterwards (the actual blocker, and its cause)**
- After the upgrade the box answered ARP but not IPv4, and SSH was gone. That
  was **not** a failed flash. Two independent faults:
  1. The LAN address had been written with **no netmask**, so it parsed as
     `/32` and the IPv4 routing table was empty. Confirmed over link-local
     IPv6 (`fe80::…`), which still worked.
  2. The **host** NIC had IPv6 administratively disabled and carried a stale
     `known_hosts` entry from a different device on the same address.
- Fix: enable IPv6 on the host with RA acceptance off, use a session-scoped
  `known_hosts` rather than deleting the shared entry, then commit **one**
  UCI change — `network.lan.netmask=255.255.255.0` — with a readback, and only
  then reload networking. Strict IPv4 and IPv6 SSH both verified afterwards.
- **Persistence proven by a real cold boot**: the operator power-cycled the
  unit; after boot the `/24` netmask, the DHCP suppression and 25.12.4 were all
  still in place with a fresh uptime. Upstream correction posted.

**Keeping the fleet safe**
- DHCPv4, DHCPv6, RA and NDP are all disabled on the router (`dhcp.lan.ignore=1`,
  `dhcpv4=disabled`, `dhcpv6=disabled`, `ra=disabled`, `ndp=disabled`), restarted
  only dnsmasq+odhcpd, and confirmed by passive capture: zero DHCP offers, zero
  RAs. The router was never bridged into the production LAN; it is reachable
  over a point-to-point NIC instead.

**Card work (read-only)**
- Built `lpac 2.3.0` **AT-backend-only** for `mipsel_24kc` with the verified
  25.12.4 SDK: **77,288 bytes, `NEEDED libc.so` only**, no RPATH, no
  `libeuicc*.so`, no driver directory. Staged to `/tmp`, remote SHA-256
  matched, runs natively.
- **Gate 0 passed.** With `LPAC_APDU=at LPAC_APDU_AT_DEVICE=<AT tty>`:
  - `lpac chip info` → EID read, eUICC SVN 2.2.2, firmware 4.2.0,
    431,434 bytes free NVM, `rspCapability` includes **`testProfileSupport`**.
  - `lpac profile list` → `[]` — **empty profile store**.
- So the 9eSIM is **healthy with an empty store, not damaged**. It presents a
  placeholder ICCID, which is the "no enabled profile" signature, not a fault.
  The card answering `+CME ERROR: 0` earlier was a **port/spacing** problem.

**Card / slot identification**
- Two cards are seated. Slot 1 = the physical carrier SIM (registers, has
  APNs, currently unregistered). Slot 2 = the 9eSIM, confirmed by
  `AT+QUIMSLOT=2` → `+CPIN: NOT READY` → `READY`, read back as 2 and persisted.
- **AT port is `/dev/ttyUSB2` on this boot**, but it shuffles across power
  cycles. On 25.12.x `/sys/class/tty/ttyUSB*/device/interface` is gone, so
  identify it from the parent USB interface protocol: `30` = diag,
  `40` = NMEA/GPS, AT is one of the `00` interfaces — then confirm with a real
  round trip. Treat "no reply" as "wrong port", never as "dead modem".
- Killed an **orphaned `cat /dev/ttyUSB2`** left by an interrupted session that
  was holding the port. Check `fuser /dev/ttyUSBx` and `ps w | grep lpac`
  before blaming the card.

**Transport, solved — split the APDU and HTTP legs**

This is the finding that unblocks provisioning without giving the router a
WAN. `lpac`'s APDU driver and its HTTP driver are independent, so they do not
have to run on the same host:

- APDU stays **local on the router** (`LPAC_APDU=at`, `/dev/ttyUSB2`) where the
  tty is fast.
- HTTP is relayed to the **provisioning host** (`LPAC_HTTP=stdio`), which does
  the real HTTPS and returns the response as JSON on stdout.

`driver/http/stdio.c` speaks a trivial JSON protocol (`{"type":"http",
"payload":{"url","tx","headers"}}` → `{"rcode","rx"}`), and
`driver/apdu/stdio.c` is *always* compiled in — so the AT-only binary already
contains the HTTP stdio driver. No curl on the router, no WAN, no NAT.

Why not tunnel the APDU instead: a full profile transfer is hundreds of APDUs,
each needing an 8 s modem dwell; over an ssh pty that is hours and it does not
finish. Relaying JSON keeps the fast leg fast and puts only request/response
bodies on the wire.

A first attempt at this split still failed at
`es10b_load_bound_profile_package` → `unknown,unknown`, but that attempt ran
over the slow ssh-pty APDU path; the session then cancelled cleanly and the
card was left with **zero profiles, verified** — no partial write. The
rebuilt transport completes `profile list` in seconds.

**The hang, root-caused (`lpac` v2.3.0 AT backend)** → issue **#862**

`lpac` hangs forever at 100 % CPU with `AT_DEBUG:` printing thousands of empty
lines. `driver/apdu/at.c:42` `at_expect()` never checks the `fgets()` return
value; on EOF it returns NULL, `buffer` stays empty, nothing matches
`OK`/`ERROR`, and `while (1)` spins.

A/B proof on the target, same binary, same card:

```
port VMIN=0  ->  fgets=NULL errno=0 feof=1   ->  spins forever, no output
port VMIN=1  ->  same command,  5 s, full chip info JSON
```

Trigger: `at_expect()` inherits whatever read discipline the tty is in — the
driver calls `fopen(dev,"r+")` and **never sets termios** (no
`tcsetattr`/`cfmakeraw` anywhere under `driver/apdu/`). So anything that leaves
the port non-blocking (`uqmi`, `mbimcli`, a stray `cat`) makes `lpac` hang
permanently. Workaround on-device: set `VMIN=1` before invoking `lpac` — this
image has no `stty`, so a tiny static helper is required.

Note: upstream `main` has already rewritten this path
(`driver/apdu/at_cmd_unix.c`, #311/#395/#396) and does check the read result.
But **v2.3.0 is the only release** (Aug 2025) and is what the OpenWrt feed
ships, so the bug is live for every distro consumer.

## 2. What did not work

- **The documented `ssh://` eSIM transport cannot run on 25.12.x.** Its remote
  relay starts with `stty -F <tty> raw -echo`, and this image has **no
  `stty`**. Also absent: `timeout`, `socat`, `microcom`. `opkg` is gone
  (`apk` only), and fractional `read -t 0.5` is rejected. → issue **#856**.
- **`lpac <subcommand> --help` is not inert.** It initialises the eUICC (opens
  the APDU device, selects ISD-R) *before* printing usage, so on a contended or
  wrong port it hangs forever — with no `timeout(1)` on the box to bound it.
  This stranded the AT tty once. → issue **#857**.
- **The feed `lpac` package is the wrong shape here**: its metadata pulls
  `libcurl4`, `libpcsclite`, `pcscd` and `libmbim` because the feed build
  enables every backend, and none of those are present on the image. Overlay
  headroom is only ~14.5 MB. Hence the AT-only static build.
- **`uqmi` cannot answer the slot/card question**: `--uim-get-sim-state`
  exists but the query returns `Failed to connect to service` on this
  configuration. Slot identification needed AT.
- **Multimeter probing of the RJ45 to "certify" 802.3at was wrong advice** and
  was retracted — an unloaded reading cannot certify it. Power safety was
  settled from the datasheet/label (48 V DC, 0.5 A, 13 W max) and the switch
  spec instead.
- **A generic `patchelf` RPATH recipe does not work.** Upstream's top-level
  `CMakeLists.txt` sets `CMAKE_INSTALL_RPATH` *after* the toolchain file, so a
  toolchain-level `CMAKE_SKIP_RPATH` is overridden. All three RPATH flags must
  go on the **cmake command line**, and `-static-libgcc` must be added or the
  link records `NEEDED libgcc_s.so.1` (absent from the image).
- **`lpac` disables TLS verification outright.** v2.3.0 hard-codes
  `CURLOPT_SSL_VERIFYPEER=0` and `VERIFYHOST=0`; `main` makes it configurable
  but still defaults to off. The reason is real — SM-DP+ endpoints present a
  GSMA-private chain (`GSM Association - RSP2 Root CI1`) and send no
  intermediate — but "verify nothing" is not the only alternative. The relay
  here pins the RSP's SPKI instead (verified both ways: correct pin accepted,
  wrong pin raises `SSLError`). → issue **#865**.

**The profile install itself — four attempts, all failed, and it is not transport** → §3

The stages, in order, so the next attempt does not re-walk them:

| # | Reached | Failed at | Cause |
|---|---|---|---|
| 1 | — | `activation_code: invalid` | **my bug**: relay joined argv unquoted, remote shell ate `$rsp`/`$QRF`, lpac parsed token `1.truphone.com-SPEEDTEST` |
| 2 | — | `CERTIFICATE_VERIFY_FAILED` | **my bug**: relay used the public CA store against a private-CA host |
| 3 | `getBoundProfilePackage` → **27,768-byte BPP fetched** | `es10b_load_bound_profile_package` → `unknown,unknown` | genuine card/ES10b failure |
| 4 | `authenticateServer` | `es9p_authenticate_client` → `Refused` | activation code now consumed by #3 |

Attempt 3 is the decisive one: fast local APDU, correct quoting, working pinned
TLS, full `initiateAuthentication` → `authenticateClient` → `getBoundProfilePackage`
all HTTP 200, a real 27 KB BPP in hand — and the install still failed. **That
eliminates transport as the cause.** The earlier "it's the slow ssh-pty APDU
path" theory is dead.

The signature matches estkme-group/lpac#474 (ES10x MSS splitting the initial BPP
segment), but the MSS experiment here is **inconclusive, not negative**: attempt
4 (MSS 250) was refused at authentication and never reached the load stage, so
MSS 250 remains untested against this card.

`lpac` also reports `unknown,unknown` rather than the card's actual
`ProfileInstallationResult`, so the useful evidence is being discarded by the
client — reading the real ES10b error is the highest-value next step, ahead of
any further tuning.

**Why `unknown,unknown` is worse than it looks.** In `euicc/es10b.c` the
ProfileInstallationResult *is* decoded — `0x80` becomes a `bppCommandId` and
`0x81` an `errorReason`, both mapped through `euicc/tostr.c`. But
`ES10B_BPP_COMMAND_ID_UNDEFINED` and `ES10B_ERROR_REASON_UNDEFINED` both render
as the literal string `"unknown"`. And every early `goto err` in
`es10b_load_bound_profile_package_tx()` — a failed `unpack_find_tag` for `BF37`,
`BF27`, `BF2F`, `A2`, or a failed `unpack_first` — returns `-1` with the struct
still holding those UNDEFINED sentinels.

So `unknown,unknown` means **either** "the card reported an error code this
build does not know" **or** "the card's response did not parse at all", and the
two are indistinguishable in the output. That ambiguity is itself a bug worth
reporting: it hides exactly the information needed to diagnose an install
failure. Capturing the raw ES10b response bytes (or logging the failing tag
and the first bytes of `respbuf`) would resolve it in one run.

**Cost of this session: the free test code is spent.** `QRF-SPEEDTEST` now
returns `Refused` at `authenticateClient` (HTTP 200, 207-byte refusal payload),
which lpac's own error table maps to the matchingID/AC-token class (8.2.6/3.8,
"MatchingID refused") — i.e. the
SM-DP+ will no longer open a session for it with this eUICC. Three of the four
attempts were lost to tooling bugs, not to the card. That is the rule to
internalise: **fix and prove the transport against a cheap read (`profile list`,
`chip info`) before spending a single-use activation code on it.**

Card state was verified `profile list → []` after every attempt: nothing
written, no partial profile, no paid spend, no router config changed.

## 3. What still needs doing

**Blocked on a valid activation code, not on tooling.** The transport works
(§1) and is proven against cheap reads; the free test code is spent (§2).

1. **Get a fresh activation code.** `QRF-SPEEDTEST` now returns `Refused` at
   `authenticateClient` and cannot be reused with this eUICC. Source a new free
   or trial profile (a real order from the RSP, not a documented shared code) —
   this is the only hard blocker.
2. **Fix the ES10b path BEFORE spending it.** Highest value first:
   - Read the card's actual `ProfileInstallationResult` instead of the
     `unknown,unknown` that `lpac` v2.3.0 prints. The client is discarding the
     one piece of evidence that says *why* the install failed.
   - **Already built and deployed:** `/usr/bin/lpac` on the router is now a
     v2.3.0 build with an `LPAC_DEBUG_ES10B=1` diagnostic that hex-dumps the raw
     ES10b response before parsing (`euicc/es10b.c`), so the next attempt that
     reaches the load stage will report what the card actually sent instead of
     `unknown,unknown`. Verified present in the binary and the build still
     passes `profile list`. It could not fire on the last attempt because that
     one was refused earlier, at `authenticateClient`.
   - Consider building from upstream `main`, which has the rewritten
     `at_cmd_unix.c` (bounded reads, no `fgets` spin) and configurable TLS.
   - Then test MSS as a controlled variable. Only the default **120** has
     actually been exercised against this card; 250 was never reached.
3. **Prove any transport change against a cheap read first** — `profile list`
   and `chip info` cost nothing and exercise the same path end to end. Every
   one of the three wasted attempts in §2 would have been caught that way.
   **Never spend a single-use activation code on an unproven transport.**
4. **Then** the $1 nadanada, then silent.link. Verify enable + registration
   between each step. `AT+CSIM`/`CGLA` spacing stays **8 s or more**.
5. **Re-verify DHCP suppression after any WAN work** — `ifup wan` must not
   re-enable the LAN DHCP server. Attribute any DHCP offer by source MAC.
6. **Decide the production transport** (#856). #861 has since landed on master
   and marks the `ssh://` relay 24.10-era/broken on 25.12.x, so the playbook is
   no longer recommending it. The APDU/HTTP split (§1) is the working
   alternative that needs neither `stty` nor a WAN; the remaining question is
   which one gets productised into a script. The relay driver should ship with
   SPKI pinning rather than inheriting lpac's verify-off behaviour (§2, #865).
7. **Upstream the `lpac` findings** (#862, #865) — filing externally is blocked
   by conwrt AGENTS.md "External Repository Etiquette" and needs a human. Both
   are worth sending: a reader that spins forever on EOF, and a TLS layer that
   verifies nothing by default.
