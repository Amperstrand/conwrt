# Device 1 Recovery Documentation — 2026-11-10

## The problem

After the backup campaign (2026-11-09), ~5 deliberate kernel panics from reading
mtd1/mtd2 (known crasher partitions) left the modem unable to register its
services (QMI/AT) on any boot. The SMEM/IPC channel table came up truncated
on every boot — same 14 entries, same missing channels, through every reset
class (warm, cold soak, PMIC, DM-triggered). DM and adb survived; cellular
did not.

## What we tried before the recovery (all failed to restore cellular)

| Attempt | Result |
|---|---|
| 7 warm reboots (adb reboot) | Same failure |
| Power-key cycle (5s) | Same failure |
| Cold power removal (120s) | Same failure |
| Cold power removal (10 min, true cold) | Same failure |
| DM DLOAD/0 reset frame | Same failure |
| DM CONTROL_F offline/online | Same failure |
| EFS writes (aid_list zeroed, lpa_support=1) | Applied but didn't fix cellular |
| MCM service restarts | atcop fails on smd8 sysfs (persistent) |
| Subsystem restart (sysfs trigger) | Not available on this kernel |

## What fixed it: bootloader trigger → TFTP fence → full re-provisioning

The **volume-not-found handler** (mechanism A) is the bootloader's built-in
recovery: when the kernel volume is missing from the UBI, it builds a network
identity, TFTP-pulls a fresh image, and self-flashes. This re-runs the complete
boot initialization from a genuinely clean state.

### Step-by-step recovery log

1. **Trigger preparation**:
   - `mtd erase rootfs` (full erase of the 30MB rootfs partition)
   - `mtd write /tmp/trigger.img rootfs` (393,216B kernel-volume-less UBI)
   - Verified: "UBI#" magic present, NO kernel volume in UBI scan

2. **Fence setup** (on ai-legion, bay 1007 VLAN):
   - Image: root_uImage (38,797,312B, sha256 `01f6f7bc…`) — the proven Nov 6 image
   - Bound to `192.0.0.1:69` on `enp2s0.1007`
   - **BLOCKER FOUND AND FIXED**: iptables default-DROP policy was silently
     discarding the bootloader's TFTP requests. Fix: `iptables -I INPUT -i
     enp2s0.1007 -p udp --dport 69 -j ACCEPT`

3. **Recovery sequence**:
   - Router rebooted → U-Boot saw no kernel volume → recovery fired
   - Bootloader built identity `192.41.54.191`, sent TFTP RRQ to `192.0.0.1:69`
   - Fence served 38.8MB in ~10 seconds (blksize 1468)
   - Bootloader confirmed: `"OK:zte blank download is done"`
   - Router rebooted into fresh OpenWrt 22.03.0-rc5 (the original flash image)

4. **Post-recovery**:
   - Router came up at 192.168.1.1 (default) — needed a power cycle for the
     Ethernet PHY quirk (carrier up, zero frames — the documented species
     cold-boot behavior)
   - Accessible via IPv6 link-local on the WAN port (fe80::caea:f8ff:fec1:7ec6)
   - **Modem AT responding**: "ZTE CORPORATION, MF286DMODULE, BD_TELIAMF286DV1.0.0B12"
   - Cellular hardware detected (ttyUSB0-2, USB 19d2:1485)

## Key lessons from this recovery

1. **The firewall was the hidden blocker** — tcpdump sees packets BEFORE
   netfilter; the fence "worked" in local tests but the bootloader's requests
   were silently dropped. Always check iptables when a service works locally
   but not remotely.

2. **`mtd write` does NOT erase the full partition** — it only erases the
   blocks it writes to. The first trigger attempt failed because the old
   kernel volume survived in the unwritten blocks. Always do `mtd erase`
   separately first.

3. **The PHY cold-boot quirk requires a power cycle after any major flash
   event** — this is now documented three times on this species.

4. **The bootloader's volume-not-found handler is the definitive recovery
   mechanism** — more reliable than any Linux-side reset. This should be the
   first tool, not the last resort.
